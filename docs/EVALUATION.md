# Evaluation

The page to read when the question is "how do you know these thresholds are right?" or
"what is the precision of this check?".

Three generated reports sit behind it, each regenerable and each naming the sample it was
measured on:

| file | what it answers | generated by |
|---|---|---|
| [`evaluation/sensitivity.md`](evaluation/sensitivity.md) | How far the triage split moves when each threshold moves | `make sensitivity` |
| [`evaluation/metrics.md`](evaluation/metrics.md) | Per-check precision, recall and F1 against the fault harness | `make metrics` |
| [`evaluation/benchmarks.md`](evaluation/benchmarks.md) | Wall clock per phase, and peak memory | `make metrics` |

---

## Why this exists

**The regime model's parameters were stated, not justified.** `active_bar_ratio = 0.5`,
`daily_thin_volume_ratio = 0.01`, `outlier_mad_k = 8.0` and their three siblings decide
every severity this tool assigns, and the product's headline claim — 44 daily findings
need a human, 14,974 are correct settlement prints and exchange holidays — is downstream
of all six. ADR-4 said as much and named the risk ("a wrong threshold flips a severity")
without quantifying it. For a model-risk reader that is the wrong way round: the number
most worth challenging was the one with no sensitivity behind it.

**Precision and recall were asserted, never reported.** `tests/support/faults.py` has
measured both since the engine was written — `assert_findings_match` requires every
expected finding *and* forbids every unexpected one — but it does so inside tests, so the
evidence existed and the artifact did not. A reviewer cannot read a confusion matrix out
of a pytest exit code. The quoted performance figures had the same problem in a worse
form: 5.5 s, 11 ms and ~1.3 GB lived only in prose, where nothing could contradict them.

## How to regenerate

```bash
make sensitivity   # ~4.5 min on data/raw; ~2.5 s on the committed fixtures
make metrics       # ~4 s for metrics.md, plus ~18 s of timings
make metrics METRICS_FLAGS=   # metrics.md only, leaving benchmarks.md alone
```

`sensitivity.md` and `benchmarks.md` were generated from `data/raw` (the pinned
HuggingFace sample, `make fetch`; 84 candidate files, 100.7 MiB as `benchmarks.md`
measures it). `metrics.md` is corpus-independent: it reads nothing but synthetic bars,
which is why it can be asserted byte-equal to its generator in `make test`.

The sweep degrades to the three committed parquet fixtures when `data/raw` is absent and
says so in its header, so a clean clone can run it. That fallback is what the tests use —
**`make test` still never touches the network and never reads `data/`.** A fixture run
cannot reproduce the 44-of-15,018 separation, because the fixtures hold two daily
contracts against the corpus's forty, and a test asserts the committed file says
`Corpus: data/raw` so a fixture run can never be committed under that name by mistake.

Timings are deliberately in their own file, regenerated only with `--benchmarks`. That way
a diff in `metrics.md` means detection changed — which it should not, without a reason —
and a diff in `benchmarks.md` means the machine was busy, which is expected.

## Threshold sensitivity — how to read it

**Needs a human** is a finding at ERROR or WARNING. Everything at INFO is a finding the
regime model explained.

**One-at-a-time, not a grid.** The six parameters partition by the frame they act on:
`activity_percentile`, `active_bar_ratio` and `dormant_bar_ratio` are read only by
`_minute_regimes`; `daily_thin_volume_ratio` only by `_daily_regimes`. A six-way grid at
5–7 levels would be 15k–117k configurations — days of wall clock at ~5.4 s a minute pass —
laying independent axes out as a hypercube. OAT also answers the question a reviewer
actually asks, one parameter at a time. The 67 configurations actually run take 4.5 minutes.

**Control pairs.** A frequency that does not read a parameter is still swept at that
parameter's two extremes, flagged `control`. Two runs demonstrate the no-op empirically
where seven would spend minutes confirming something the code already implies — and a
control row that *moved* would mean the engine had started reading a threshold somewhere
the generator does not know about. None moved.

**Where the defaults sit.** Every default is interior to its swept range, and the grid puts
the shipped `(0.5, 0.1)` at its centre, so the tables show both directions from each one.

### What the sweep found

**The daily headline is very nearly threshold-independent.** Across all 21 daily
configurations the needs-a-human count is **44 in 20 of them**, and 46 in the twenty-first.
The 5 ERROR / 39 WARNING split is byte-identical in those 20. The exception is
`daily_thin_volume_ratio = 0.0`, which is degenerate rather than merely extreme: a THIN
cutoff of zero abolishes the THIN bucket entirely (16,824 ACTIVE sessions against the
default's 8,516), which widens every contract's expected-coverage window and takes
`missing_session` from 1 WARNING to 3. So the honest statement is not "the 44 is robust"
but something sharper: **within this corpus the 44 does not depend on a threshold at all
unless one is set to a value that removes a regime.**

**`invalid_ohlc`'s 5 ERROR / 38 WARNING is structural, not parametric — it cannot be moved
by any of the six.** The check downgrades to WARNING in a DORMANT session, and on a daily
frame `_daily_regimes` makes a session DORMANT when `session_volume <= 0`, against a
**literal** `0.0` rather than a configured value. `daily_thin_volume_ratio` is the THIN
cutoff, and `regime_severity` treats THIN exactly like ACTIVE for this check. So those
forty-three findings split on an observation — was anything traded that day? — and not on
a parameter, at every value in every swept range. (The report's thirty-ninth WARNING is
`missing_session`'s, and that one *is* parametric: it is the one that becomes 3 at
`daily_thin_volume_ratio = 0`.) This was not anticipated; the sweep was built expecting
that threshold to move the `invalid_ohlc` split, and a test now pins the fact that it
cannot.

**Minute frequency is the opposite, and `max_gap_minutes` dominates it.** Needs-a-human
runs from 7,156 at `max_gap_minutes = 30` to 799,731 at 1 — a factor of 112 — and
`intrabar_gap` accounts for all of it. `active_bar_ratio` spans 56,296 to 223,543 and
`activity_percentile` 62,985 to 264,790. The minute report is a magnitude estimate and
should be read as one; the daily report is the one the product's claim is drawn from, and
it is the stable one.

**`dormant_bar_ratio` moves nothing, on either frequency, and that is a finding.** Every
swept value reproduces the default's findings, bars and severity split exactly, for every
check. It is not a broken sweep, and the sessions column proves it: at minute frequency
the DORMANT bucket goes from 0 sessions at ratio 0 to 7,465 at 0.3 — half the corpus
reclassified — with the ACTIVE count pinned at 6,139 and not one finding changing. The
mechanism is that **only `Regime.ACTIVE` is ever read.** Three checks consult the regime
(`intrabar_gap`, `stale_bar`, `outlier_return`) and all three test `== Regime.ACTIVE`;
`ActivityProfile.active_span()`, which bounds `missing_session`'s expected coverage, is
ACTIVE-only too. THIN and DORMANT are therefore indistinguishable to every consumer, and
`dormant_bar_ratio` is the only threshold that moves solely the boundary between them.

What it *does* still reach is evidence. `stale_bar` puts the `regime` string in its message
and `dormant_threshold` in its evidence, both taken from the profile, so the text a user
reads does change with this parameter even though the count and the severity cannot. The
threshold is not dead — it is a labelling knob for the Overview heatmap, which renders
DORMANT and THIN as distinct buckets. Worth knowing before anyone tunes it expecting
triage to respond.

**The one interaction turned out not to be one.** The `active_bar_ratio ×
dormant_bar_ratio` grid exists because those two are the lower and upper cutoffs of the
same three-way split, which made them the only pair that could plausibly interact. Every
row of the grid is constant across all five `dormant_bar_ratio` columns. The axes are
separable: the 25-cell grid carries nothing the two OAT sweeps over the same two
parameters do not already carry, which is the empirical case for not gridding the other
four.

**The sweep reports. No default was changed.** Nothing here argues for a different default:
the daily parameters have nothing to gain, and the minute ones are genuinely sensitive with
no external oracle to calibrate against, which is a reason for caution rather than for
tuning. If anything, the finding that `dormant_bar_ratio` cannot affect triage is an
argument for a check that distinguishes THIN from DORMANT, not for a different value.

**Limitations.** One corpus, and the defaults were chosen on it. A sweep cannot show a
threshold generalises; it can only show the answer is not balanced on a knife edge within
the range swept. The minute sweep runs each configuration over 5.3M rows once, so there is
no variance estimate — the engine is deterministic, so repetition would only measure the
machine.

## Precision and recall — methodology

29 scenarios: 4 clean frames and 25 faulted ones, covering all 19 fault types in
`tests/support/faults.py` and all 14 checks. Each scenario is one clean synthetic frame
plus zero or more faults, run through `run_checks` and scored against the `Expected`
entries the fault itself declares.

**The unit is one unit of `Expected.count` per check** — "how many bars, or for a gap how
many absent minutes, the check should account for". It is the unit `Expected` is written
in, the one `assert_findings_match` already sums on, and the only one available for two of
the fourteen checks: `missing_session` names no rows at all (`row_ids=()`), and
`intrabar_gap`'s row ids are the two bracketing *survivors* rather than the bars that
vanished. Row-level scoring would be undefined for both.

Per scenario and per check, with `want` the summed `Expected.count` and `got` the summed
reported `count`: TP = `min(want, got)`, FP = `max(0, got - want)`, FN =
`max(0, want - got)`.

**The awkward cases, and how each is handled.**

- *A fault that legitimately trips two checks.* Each check is scored independently against
  its own `want`. `AmbiguousLocalTime(passes=2)` really does trip `ambiguous_local_time`
  and `duplicate_timestamp` — under `ambiguous="earliest"` both copies land on the same
  instant — and `Expected` declares both. No special case needed.
- *Right check, wrong count.* Overlap is TP, excess FP, shortfall FN. A check reporting
  three bars where two were broken scores TP 2 and FP 1: it found the defect and
  over-reached, and the matrix says both.
- *Right count, wrong severity.* Does **not** change TP/FP/FN. Detection and triage are
  different failures and one number would hide which broke, so it lands in a separate
  `severity misses` column. A non-zero value there means the regime model mis-triaged a
  real detection.
- *Right count, wrong rows.* Same treatment, in `row-id misses`. Count agreement could
  otherwise hide a check that named the wrong bars.
- *A check that fires with no expectation at all.* False positive for its whole output —
  the `unexpected` branch of `assert_findings_match`, as a number rather than a raise.
- *Clean data.* The four zero-fault scenarios contribute precision only, and also get
  their own table. Every cell is 0.

### What the measurement found

**Recall is 1.000 for all fourteen checks, and so are `severity misses` and `row-id
misses`.** Every check detected every unit declared for it, at the right severity, naming
the right bars. The clean-data guard is 0 in all 53 applicable cells of its 14 × 4 grid —
the other three are the minute-only checks against the daily frame — across 360, 2,760,
480 and 3 bars of clean synthetic data. No check crashed.

**Precision, recall, severity and row ids are 1.000 across all fourteen checks** — but that
was not the first reading, and the first reading is the more useful thing to record.

On its first run the harness measured **`stale_bar` at precision 0.200** — TP 1, FP 4, all
four from one scenario, `ambiguous_local_time`. The check turned out to be right and the
*declaration* short:

`AmbiguousLocalTime` exists to put bars inside the repeated fall-back hour, so it cares
about the wall clock and picks a price arbitrarily — `open = high = low = close = 100.0`,
volume 10. That is a flat bar. `stale_bar` detects on the vendor's own no-range predicate,
`open == high == low == close`, deliberately *without* a volume clause (the vendor's 14,152
against 12,841 with one — see the README's oracle section), and calls a flat-but-traded bar
INFO everywhere. So it reported four genuinely flat bars at the correct severity. The fault
declares two of its three consequences.

This was worth finding, and *how* it hid is the interesting part. `assert_findings_match` is
the only thing in the suite that forbids an unexpected check, and it is never applied to
this fault. The two tests that use `AmbiguousLocalTime(bars=2, passes=2)` are
`test_faults.py`, which inspects the corrupted frame and never runs a check at all, and
`test_insights_rules.py`, which *does* run it end to end through `run_checks` — via
`support.insights.context` — but asserts only one insight rule's evidence. So `stale_bar`
has been firing on those four bars all along, inside a test that passes, with nothing
looking at the set of checks that fired. Scoring the catalogue surfaced it on the first
run.

**The declaration was then corrected, which is why the table now reads 1.000.** `Expected`
is documented as "every finding the engine must produce, and nothing more", so a list
naming two of three real consequences is a defect in the fixture, not a fact about the
engine. `AmbiguousLocalTime` now declares `stale_bar` at INFO over the same four rows, and
`stale_bar`'s four findings moved from false positive to true positive — they always were
real detections; nothing about the engine's behaviour changed.

The distinction matters, because the lazy version of this is to add an `Expected` entry for
whatever a check happened to emit, which is laundering with extra steps. So the declaration
is proved from the data rather than asserted into place:
`test_the_flat_bars_ambiguous_local_time_appends_really_are_stale` asserts the appended bars
carry `open == high == low == close` with non-zero volume — a flat-but-traded bar, INFO by
`stale_bar`'s own definition — and that the check reports exactly those row ids at exactly
that severity. `KNOWN_FALSE_POSITIVES` is now empty, and
`test_there_are_no_false_positives_anywhere` asserts the emptiness, so any future check
firing where no fault declares it fails the build instead of hiding in a green one.

That last assertion is the durable gain here. The measurement was a one-off; the guard is
permanent, and it is the guard the suite did not have.

**`wall_clock_read_as_utc` is in the catalogue precisely because it expects nothing.**
Reading a Chicago wall clock as UTC — the single mistake the whole time layer exists to
prevent — leaves the frame internally consistent: coherent bars, unique instants, dense
sessions. Every row-level check correctly reports nothing, so recall is not defined for it
and it contributes precision only. Only reconciliation between frequencies could catch it,
and `cross_frequency_mismatch` is a documented non-goal in `ARCHITECTURE.md`. The scenario
makes that blind spot visible in the numbers instead of absent from them.

**Limitation: these faults are meant to be surgical.** Each is written to violate one
invariant and leave the others intact, which is what makes the precision half mean
anything — and the `stale_bar` result above is a measured instance of one that is not. Either
way, these figures say nothing about compound defects (an outage that drops bars, stales
the ones it keeps and duplicates the recovery) and nothing about defect rates in real data.
They measure whether each check does its own job cleanly on a defect aimed at it. The
external check on that is the vendor oracle, which is a separate and stronger test:
`tests/golden/test_quality_golden.py` reproduces all four of the vendor's published
diagnostics on 40/40 daily files.

## Benchmarks

Five phases, three repeats each, min and median reported with the sample on every row —
`benchmarks.md` has the table. Peak RSS is taken once at the end and labelled as what it
is: a whole-process ceiling attributable to no single phase.

Not measured, and the artifact says so: per-phase memory (it needs a subprocess per phase
to be honest, since `ru_maxrss` only rises, and `tracemalloc` would understate Polars by an
order of magnitude); the dashboard and the HTTP API; analytics and insights.

### Quoted versus measured

| quoted in prose | where | measured | verdict |
|---|---|---|---|
| 11 ms file classification | README | 0.01 s over 84 candidate files, 100.7 MiB | reproduced |
| 13 ms file classification | `service/store.py` | as above | reproduced |
| 0.12 s daily ingest | `service/store.py` | 0.10 s | reproduced |
| 1.1 s minute ingest | `service/store.py` | 1.14 s | reproduced |
| 0.07 s daily quality pass | `service/store.py` | 0.06 s | reproduced |
| ~5.5 s minute quality pass | README | 5.15 s min, 5.43 s median | reproduced |
| 4.9 s minute quality pass | `service/store.py` | as above | reproduced (prose is at the low end) |
| **~1.3 GB peak memory** | README | **2.25 GiB** (`ru_maxrss`) | **not reproduced** |

The memory figure is the one that did not hold: the measured peak is about 1.9 times the
quoted one. The measurement is a whole-process peak after a benchmark that holds both
frequencies' bars *and* both quality reports simultaneously, which no single request does —
so it is an upper bound rather than a contradiction of a per-request figure. But the README
does not qualify its number that way, and the honest reading is that 1.3 GB is not
reproducible under any measurement taken here. The quoted numbers were left as they are:
changing a published figure is the owner's decision, not this work's, and the discrepancy
is more useful recorded than quietly corrected.

One caveat on the two ingest rows: they time `bars(frequency)` followed by a row count
collected from the lazy frame. That is what the prose figures describe, and at 1.14 s for
5.3M rows it is clearly doing real work rather than reading parquet statistics — but it is
a floor on ingestion rather than the cost of materialising every column.

### Sample sizes, once

40 contracts, 8 roots, 6 exchanges. Daily: 30,102 rows, 40 contracts, 15,018 findings.
Minute: 5,295,239 rows, 40 contracts, 158,061 findings. 84 candidate files under
`data/raw`, 80 of which are bar data; 100.7 MiB of candidates. Environment on which every
timing here was taken: Darwin arm64, 8 logical CPUs, Python 3.12.13, polars 1.44.2.
